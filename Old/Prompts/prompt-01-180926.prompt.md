# Recolección de contrato APX — Tipo A

Eres un experto en arquitectura APX de BBVA. Dado un proyecto APX de tipo `du_online`, analiza cada transacción y genera un JSON por transacción respetando exactamente `contrato\contrato-transaccion.json`.

No generes contratos de librerías. Las librerías internas solo se documentan en `TECHNICAL DATA.Accessed Libraries` de cada transacción.

## Estructura esperada

```
artifact/
  transactions/
    <UUAATXXXYYZZ>/
      pom.xml
      src/main/resources/
        <UUAATXXXYYZZ>.xml
        multilanguage-ES.properties
      src/main/java/com/<uuaa>/
        <Nombre>Transaction.java
        Abstract<Nombre>Transaction.java
apx.json
```

## Contrato de referencia

Lee `contrato\contrato-transaccion.json` y respeta exactamente sus claves, orden, tipos y estructuras. No agregues campos de análisis al JSON final.

Valores válidos para campos seleccionables:

- `Country`: `ES`, `MX`, `PE`, `CO`, `US`, `GL`, `AR`, `Common`.
- `Asynchronous?` y `Transactional?`: `Yes`, `No` o `"NO HAY INFORMACIÓN SUFICIENTE"` cuando no exista evidencia suficiente.
- `Severity`: `04 - WARNING`, `06 - ERROR NO ROLLBACK`, `08 - ERROR WITH ROLLBACK`.
- `APX data type`: `compound`, `double`, `long`, `string`, `file`, `date`, `boolean`, `dto`.
- `Mandatory?`: `Yes`, `No`.

## Análisis de cada transacción

Para cada módulo `artifact/transactions/<ID>`:

1. Confirma que existen el XML de definición y la clase concreta `*Transaction.java`.
2. Lee `src/main/resources/<ID>.xml` como fuente primaria de identidad, descripción y parámetros.
3. Lee la clase concreta para reconstruir el flujo, librerías invocadas, errores, asincronía, transaccionalidad y eventos.
4. Lee `Abstract*Transaction.java` solo como respaldo para relacionar getters/setters con nombres del XML.
5. Lee `multilanguage-ES.properties` para resolver descripciones de errores.
6. Para cada librería invocada, lee su interfaz y únicamente el método llamado. Lee la implementación solo cuando sea necesario para describir la llamada o los errores que el flujo recibe o propaga.
7. No uses archivos de `target/` mientras exista su equivalente en `src/`.

### Clasificación de evidencia

Clasifica internamente cada valor:

- **EXPLÍCITO**: aparece directamente en una fuente del proyecto.
- **DERIVADO**: se obtiene siguiendo inequívocamente el flujo o aplicando un mapeo definido aquí.
- **NO EXPLÍCITO**: no existe evidencia suficiente o requiere una suposición.

Estas etiquetas son solo control interno y nunca deben aparecer como claves o valores del JSON. Cuando no haya evidencia suficiente, usa `"NO HAY INFORMACIÓN SUFICIENTE"`; para colecciones sin elementos demostrados, usa `[]`.

| `EXECUTION FLOWS - DETAILED DESCRIPTION` | Flujo funcional ordenado | Cuerpo de `execute()` | Métodos privados y método de librería invocado; describir solo comportamiento observable | DERIVADO |

### Mapeo explícito XML → tipo APX

Aplica la tabla a entradas y salidas:

| XML | Tipo APX |
|---|---|
| `<parameter type="String">` | `string` |
| `<parameter type="Long">` | `long` |
| `<parameter type="Double">` | `double` |
| `<parameter type="Boolean">` | `boolean` |
| `<parameter type="Date (...)">` o `<date>` | `date` |
| `<dto>` | `dto` |
| `<list>` o estructura compuesta | `compound` |
| `<file>` | `file` |

### Expansión recursiva de parámetros

Los arrays `PARAMETERS.Input Parameters` y `PARAMETERS.Output Parameters` son planos, pero deben representar el árbol completo definido por el XML. Recorre recursivamente todos los elementos descendientes de `<paramsIn>` y `<paramsOut>` y genera una fila para cada elemento representado:

1. Conserva la fila del elemento raíz, incluidos los parámetros simples, DTOs y listas.
2. Para cada `<dto>` o `<list>`, agrega también una fila para el contenedor y continúa recorriendo sus hijos.
3. Para cada `<parameter>` hoja, agrega una fila con su tipo XML convertido según la tabla anterior.
4. Construye `Name of APX field` concatenando los nombres XML con puntos (`.`), desde el elemento raíz hasta el elemento actual. Usa el nombre exacto de `@name` de cada contrato; no sustituyas la raíz por un alias funcional común.
5. Respeta el orden numérico de `@order` entre hermanos en todos los niveles.
6. La obligatoriedad de cada fila procede del atributo `@mandatory` del elemento XML que esa fila representa. No heredes la obligatoriedad del padre.
7. En una `<list>`, no agregues índices de elemento. Si el DTO hijo es un placeholder técnico con `name="Type"`, omite únicamente ese segmento de la ruta y continúa con sus campos. Por ejemplo, el campo `itemField` debe llamarse `rootInput.items.itemField`, no `rootInput.items.Type.itemField`.
8. Para una lista, usa `compound` como `APX data type`, ya que `list` no es una opción válida en el contrato de transacciones. Para sus DTOs usa `dto` y para sus parámetros hoja usa el tipo correspondiente.

Ejemplo de expansión genérica:

```json
"Input Parameters": [
  {"Name of APX field": "rootInput", "Mandatory?": "Yes", "APX data type": "dto", "Description": "..."},
  {"Name of APX field": "rootInput.simpleField", "Mandatory?": "Yes", "APX data type": "string", "Description": "..."},
  {"Name of APX field": "rootInput.nestedDto", "Mandatory?": "Yes", "APX data type": "dto", "Description": "..."},
  {"Name of APX field": "rootInput.nestedDto.numericField", "Mandatory?": "Yes", "APX data type": "double", "Description": "..."},
  {"Name of APX field": "rootInput.items", "Mandatory?": "No", "APX data type": "compound", "Description": "..."},
  {"Name of APX field": "rootInput.items.itemField", "Mandatory?": "No", "APX data type": "long", "Description": "..."}
]
```

Si existe una salida compuesta, aplica el mismo procedimiento a su nombre real, por ejemplo `rootOutput.nestedDto.outputField`. Los nombres `rootInput`, `nestedDto`, `items` y los demás del ejemplo son ilustrativos: siempre deben sustituirse por los valores reales de `@name` del XML analizado. El ejemplo usa `"..."` solo para abreviar las descripciones; el JSON final debe incluir descripciones basadas en la evidencia disponible o `"NO HAY INFORMACIÓN SUFICIENTE"`.

No elijas un tipo por semejanza si no existe una equivalencia explícita.

### Redacción del flujo de ejecución

Describe el flujo en este orden:

1. Entrada y validaciones.
2. Decisiones y ramas.
3. Librerías y métodos invocados, datos enviados y uso de respuestas.
4. Errores, severidad y acción posterior.
5. Salidas y escenarios en los que se asignan.

No uses frases vacías como «ejecuta la lógica» o «procesa los datos». Si una parte no puede determinarse, indícalo o usa `"NO HAY INFORMACIÓN SUFICIENTE"`.

### Procedimiento obligatorio para Error Management

El objetivo es obtener el conjunto exacto de errores del flujo de esta transacción, no el inventario completo de errores del proyecto o de la librería.

Antes de redactar `TECHNICAL DATA.Error Management`, sigue estos pasos en orden:

1. Desde `execute()`, identifica cada fuente real de errores del flujo:
  - errores propios de la transacción, emitidos directamente por esa clase;
  - errores propagados por cada llamada `Library.method(...)` realmente ejecutada.
2. Para cada llamada a librería, sigue solo el método exacto invocado y los métodos auxiliares alcanzables desde él. No leas otros `execute*` de la misma librería como si pertenecieran al mismo flujo.
3. Construye internamente una tabla mínima con una fila por error encontrado en el flujo alcanzable, usando este formato fijo:
  - `Error Code`
  - `Dónde aparece primero`
  - `Condición que lo dispara`
  - `Cómo llega al advice de la transacción`
4. Un código solo puede entrar en el JSON si encontraste una fila completa en esa tabla. Si falta cualquiera de los cuatro datos, el código queda fuera.
5. Considera como evidencia válida solo estas apariciones dentro del flujo alcanzable:
  - `addAdvice(...)`
  - `addAdviceWithDescription(...)`
  - `throw new ...Exception(codigo, ...)` que luego es capturada y convertida en advice
  - excepciones propagadas hasta la transacción y convertidas allí en advice
6. No uses como evidencia suficiente por sí solos:
  - constantes de error
  - archivos `properties`
  - README, comentarios o documentación
  - tests
  - nombres de métodos, nombres de variables o nombres de estados
7. Si la transacción define constantes locales de error, no las trates como fuente de verdad. Solo inclúyelas si el flujo ejecutable realmente emite esos mismos códigos o si la transacción compara esos códigos contra advices que la librería puede devolver.
8. Si una librería es compartida por varias transacciones, no heredes al contrato actual errores de otros métodos de esa librería. El contrato actual solo puede usar errores del método exacto invocado.
9. Si un `validator`, `repository` o helper es compartido, conserva solo los errores alcanzables desde el método concreto en análisis.
10. No consolides dos códigos distintos aunque sus descripciones sean parecidas. Si el código lanza `ABKO...01` y `ABKO...02` para condiciones diferentes, ambos deben existir por separado.
11. Haz una comprobación bidireccional obligatoria antes de redactar el JSON:
  - cada código encontrado en la tabla interna aparece una vez en `Error Management`;
  - cada código de `Error Management` existe en la tabla interna;
  - si sobra o falta uno, el resultado es inválido y debes corregirlo antes de entregar.

Reglas de descarte obligatorias:

- Si un código está definido pero no aparece en el camino ejecutable del método, no lo incluyas.
- Si el flujo no contiene una validación, no inventes el error asociado aunque parezca lógico por negocio.
- Si el flujo no contiene una rama sobre hijos, restricciones, tipos, sincronización o estados adicionales, no los menciones ni en `Error Management` ni en `EXECUTION FLOWS - DETAILED DESCRIPTION`.
- Si la transacción solo revisa `getAdviceList()` para asignar severidad, eso no crea nuevos errores posibles; solo confirma que propaga advices ajenos.
- Si el código de error pertenece a otro método de la misma librería, a otra transacción, a código legacy o a una versión futura, descártalo.

Para la descripción de cada código, usa la primera evidencia disponible en este orden:

1. Texto pasado a `addAdviceWithDescription(...)` o a la excepción del camino alcanzable.
2. `multilanguage-ES.properties` de la transacción o de la librería implementadora.
3. Descripción directa de la constante asociada al código.
4. `"NO HAY INFORMACIÓN SUFICIENTE"` si no hay texto verificable.

Conserva el significado y los placeholders de la fuente. No agregues estados, condiciones ni funcionalidades que no aparezcan en el código ejecutable. Si el texto de la fuente contiene `%s`, conserva ese placeholder; no lo reemplaces por valores inventados ni por una descripción de otra rama.

Antes de cerrar el análisis de una transacción, sintetiza internamente el resultado con esta estructura de control:

- `Errores propios de la transacción`: lista vacía o códigos emitidos directamente por la clase de transacción.
- `Errores propagados por librería/método`: una lista por cada llamada `Library.method(...)`.
- `Códigos descartados`: constantes o descripciones localizadas pero no alcanzables desde el flujo real.
- `Control de completitud`: `sin sobrantes` y `sin faltantes` entre la tabla interna y el JSON final.

Solo después de esa síntesis redacta `Error Management` y el flujo final.

## Reglas de recolección

- Genera una fila por cada elemento de `<paramsIn>` y `<paramsOut>` y por cada descendiente anidado (`parameter`, `dto`, `list` u otro), usando la ruta completa en `Name of APX field`.
- Conserva las filas de los contenedores y de los parámetros hoja; no descartes un DTO o una lista por tener campos internos.
- Para listas, omite el placeholder `Type` de la ruta y usa `compound` como tipo APX.
- Conserva el orden indicado por `@order` en cada nivel del árbol.
- Una dependencia del POM no equivale a una librería accedida.
- Asocia errores únicamente con caminos que realmente puede producir o propagar la transacción.
- Si `multilanguage-ES.properties` está vacío, continúa con las fuentes de respaldo.
- La ausencia de evidencia no permite elegir automáticamente `No` para `Asynchronous?` o `Transactional?`.

Antes de entregar cada contrato, verifica que los arrays de parámetros contengan las rutas anidadas esperadas por el XML, que no falte ningún DTO/lista o campo hoja, que no se hayan inventado campos y que todas las rutas mantengan el nombre raíz declarado en ese XML.

Para `TECHNICAL DATA.Error Management`, verifica antes de entregar el contrato:

- El inventario temporal se obtuvo recorriendo el método realmente invocado y sus llamadas alcanzables, no leyendo todas las constantes de la librería.
- Cada código encontrado en ese recorrido aparece exactamente una vez en el JSON.
- Cada código del JSON tiene una condición y una ruta de propagación verificables.
- No se incluyeron códigos de otros métodos, otras transacciones, documentación, versiones futuras o funcionalidades no implementadas.
- No se fusionaron códigos distintos ni se alteraron sus placeholders o condiciones.
- Si la evidencia textual no basta para la descripción, se usó `"NO HAY INFORMACIÓN SUFICIENTE"` sin inventar contenido.
